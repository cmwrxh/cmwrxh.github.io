02 · Performance Baseline

What did we measure?

Record endpoint, protocol, probe locations, network information where available, sample count, timestamps and test conditions.

Report DNS, TCP/TLS, TTFB and total response timing. Use P50/P95/P99 only when repeated sampling is sufficient; a single observation must remain explicitly labelled as such.

04 · Architecture Review

Where is the request going?

User → ISP → Network → Routing → CDN/Edge → Load Balancer → Application → API → Database → Third Party.

Document known deployment regions, CDN/edge behavior, routing observations, application architecture and relevant dependencies. Mark assumptions explicitly.

05 · Root Cause Analysis

Why is it happening?

Separate network-path latency from server processing, application work, database time and third-party dependency time.

Use traceroute and related diagnostics as supporting evidence, not automatic proof of causation from a single hop.

08 · Expected Impact

What could improve?

State projected impact only with explicit assumptions. Estimates are not customer results. Where possible, connect projections to measured baseline values.

09 · Post-Remediation Validation

Prove the change.

Repeat relevant measurements under comparable conditions. Compare before/after results and record any changed network, infrastructure or application conditions.

10 · Technical Appendix

Reproducibility record

Include targets, endpoints, protocols, timestamps, probe locations, networks where available, sample counts, diagnostic IDs, route evidence, exclusions, assumptions, limitations and customer-supplied architecture information.

Evidence rule: A reader should understand what was measured, when, where, how, and why the conclusion follows.
